# 族群批次規劃與停復牌回補

## 手動完整重抓與獨占執行（2026-10-18）

- 資料狀態頁「重抓全部資料」改用 `POST /api/v1/backfill/regrab-all`。確認後立即回應 202，由背景統一準備 5 市場 × 7 週期，共 35 個族群；全部成功後直接抓取，不需再按繼續回補。
- 新端點共用原本整張／零股 prepare 的單族群實作，但不由瀏覽器分開送 14 次 HTTP：從準備第一組到實際回補結束，全程持有同一把跨程序工作鎖，避免組與組之間、準備與開始之間被另一個 API／CLI 回補插入。
- 若已有 API、排程、獨立腳本執行或準備中，回傳 409，不替其他工作解除暫停、不重排其斷點。已排隊的續跑也須先安全暫停，才能另開完整重抓。
- 獨立腳本在規劃、改寫控制狀態、登入之前先取得同一工作鎖，並持有至重試／等候結束。暫停指令仍可在其他工作持鎖時送出。
- 準備失敗或準備過程服務中斷：顯示失敗族群及原因、保留既有 K 線與舊計畫，禁止自動抓取部分範圍；需重新按完整重抓完成準備。安全暫停若剛好發生在最後一組，會保存完整計畫但不自動開始。
- 手動「重抓全部資料／繼續回補」及明確執行的 CLI 可在週末、休市日抓**已完成交易期間**；週月線不納入未結束期間。手動意圖隨計畫保存，斷線或記憶體恢復後仍可休市日續跑。
- 每日自動排程維持交易日及週／月末規則，不因這次修改改為假日執行。所有手動執行仍須群益已連線、記憶體恢復及未手動暫停，沒有隱藏登入。
- API 控制版本需至少 7；舊服務未重啟前，前端會明確阻擋新按鈕，不能將未載入的新功能誤判為已生效。兩個原有 prepare 端點仍是「只準備、不自動抓取」。
- 原先實機第一組回報的 HTTP 500 尚缺伺服器 traceback，不能宣稱已確認其根因。新流程會將背景準備錯誤保存於控制狀態，完整 traceback 由伺服器記錄，避免只有籠統 500 而無進度資訊。

驗證：`scripts/test_backfill_recovery_offline.py --all` 封鎖真實資料庫與群益、包含跨子程序鎖競爭；`node scripts/test_data_status_frontend.cjs` 驗證單次送出／版本保護；`scripts/test_regrab_mysql_isolated.py` 在隨機隔離 MySQL 庫使用模擬群益跑準備與寫入，結束刪除隔離庫。測試不重啟正式服務。載入新版後，控制回傳版本應為 7，再測按鈕：已有工作時應拒絕；無其他工作且連線／記憶體就緒時，進度應由準備轉為抓取，週末亦可。

## 執行順序

1. 每日排程仍先同步兩組商品主檔，兩組成功才繼續。
2. 僅先保存市場 × 週期的族群清單；各族群真正開工時，才一次批次讀取逐檔根數、最早／最新 K 線及成功檢查進度。跨日或收盤後已完成交易日改變時重新規劃；同範圍重啟保留已提交區間。
3. 族群「最舊檢查日」是觀察資訊，不會強迫每檔股票從此日期重查。沒有成交不代表沒有完成檢查。
4. 所有族群先跑最新缺口。單檔太久沒更新時，每輪限量查詢後轉入慢速補齊，不阻擋其他正常股票。
5. 先處理所有族群的長缺口 catchup，再開始較舊歷史 history，避免後面市場的最新缺口被前面市場的初始化餓死。新股／尚未完成初始化的資料另於慢速輪補到設定目標（一般 1200、週 560、月 100）。有既存資料時，只從最早一根之前往回找。連續空區間達上限先保留斷點、預設延後一天再探查，不宣稱更早資料不存在；到達設定搜尋下限仍不足才結束此輪初始化並記錄根數、下限及斷點。
6. 有效空回應也算已查詢；API 錯誤、資料庫交易失敗不推進該區間。連線恢復失敗仍安全暫停，未完成工作保留。
7. 慢速工作保留 pending 及下一輪時間。API 自動恢復服務到期續跑；CLI 保持執行會等候後續輪次，也可中斷後使用 `--resume`。明確點「繼續回補」可提早續跑，但不清除斷點，也不能略過記憶體恢復門檻。

週／月仍以最後交易日已完成的期間為準，完整查詢該週／月；年度日曆及自動排程休市規則不變，手動回補可在休市日查已完成期間。不刪除、不截短既有 K 線。

## 停復牌證據與限制

使用已核對的官方 API：

- [證交所 TWTAWU](https://openapi.twse.com.tw/v1/exchangeReport/TWTAWU)：暫停／恢復交易日期及時間。
- [櫃買歷史停復牌](https://www.tpex.org.tw/openapi/v1/tpex_spendi_history)：分開公布的停牌與復牌列配對。
- [櫃買交易狀態](https://www.tpex.org.tw/openapi/v1/tpex_cmode)：只使用 `SuspensionOfTrading`，不把變更交易、處置、分盤、停券誤當停牌。

每個來源每天快取一次；盤前快照於收盤後再更新一次。失敗的來源保留舊快取及錯誤，但當日不依其過期資料跳過。缺少紀錄代表未知，不代表正常；這些來源不是所有市場／所有長期停牌的完整歷史，尤其興櫃沒有可靠證據時仍走限量查詢。Yahoo 不作唯一跳過依據，也不以抓不到 Yahoo 網頁就判定恢復交易。

只在整個查詢區間的每個交易日均有可靠「整日停牌」證據時跳過。盤中暫停或週／月仍有交易日，照常查詢。恢復日預設保留查詢。TPEx 未配到復牌的舊歷史列不推論為至今一直停牌。跳過不會憑空產生 K 線，也不會更新 API 驗證日期。

## 可選設定（不填也有預設）

### 2026-10-18：每日排程改為最新 100／10／2 根回抓

```dotenv
# 初始化、CLI 與「重抓全部」保留原目標，不降低既有資料量。
CAPITAL_DAILY_BACKFILL_TARGETS=1m:1200,5m:1200,15m:1200,60m:1200,day:1200,week:560,month:100
# 僅每日自動排程使用的新日常回抓目標。
CAPITAL_DAILY_REFRESH_TARGETS=1m:100,5m:100,15m:100,60m:100,day:100,week:10,month:2
```

每日自動排程先完成兩組商品同步，再為每檔建立獨立的 `refresh` 模式工作。日常回抓不以資料庫現有總根數當本輪達標依據，而是以本輪成功提交的、去重且期間已完成的有效回傳根數計算；本輪根數、資料與日期斷點於同一 MySQL 交易保存。重試／暫停／重啟接續原計數及游標，不因庫內已有 1200 根而跳過，也不將日常 100 根標記成初始化完成。

第一個查詢區間依交易日曆估算：日線排除週末及休市，分線用一般股票交易時段密度估算需要的交易日，週／月涵蓋完整期間。估算不是根數保證：不足時逐段往前查，達標即停止；回傳超過目標的有效資料全數保留。例如 1m 回抓目標 100，按整個日期查詢仍可能回傳 270 根。單次區間仍受 `CAPITAL_KLINE_MAX_DAYS_*` 約束，週／月執行頻率及最後交易日判斷不變。

短資料或空回應仍遵守每檔／每輪預算、連續空區間退避及有限歷史搜尋下限；日常排程不在同輪順帶補滿 1200／560／100。舊的初始化／完整範圍工作不被本模式覆寫或標為 superseded，保留供另行回補；超過本輪最近根數範圍的長缺口，需另行使用歷史回補流程，不代表全部歷史已補齊。相同已檢查的交易日期／期間不重複排入；尚未完成的同期間 refresh 即使已檢查最新日期，仍保留續跑。

不新增正式資料表或改欄位，沿用既有工作表、`candle_backfill_progress`、`candle_batch_work`，由 mode 區分日常工作。一般／零股資料表分流不變，歷史來源仍有本文件末尾所述的整股成交限制。畫面會顯示「日常回抓目標」及「本輪回抓目標」，初始化目標另計。

本次只套用到每日自動排程，手動 `/backfill/refresh-stale`、CLI、`prepare`／完整重抓保持原語意。修改 `.env` 後需要自行安全重啟 API 才會載入；已準備的舊工作不會被直接改成新大小，既有 K 線不刪除。本次沒有重啟或觸發真實群益抓取。

新增驗證：`scripts/test_daily_refresh_mysql_isolated.py` 使用假群益及隨機測試庫，驗證日常回抓的寫入、初始化分離、續傳與交易回滾，結束會刪除測試庫，絕不退回正式庫測試。

### 登入帳密與本機設定

現有 CLI 會讀取 `CAPITAL_USER_ID`、`CAPITAL_PASSWORD`、`CAPITAL_AUTHORITY` 完成登入；FastAPI 啟動與背景恢復不會僅因 `.env` 有帳密就自動登入。本次沒有新增或啟用自動登入。

### 每輪工作額度

```dotenv
CAPITAL_BACKFILL_JOB_WINDOW_BUDGET=3
CAPITAL_BACKFILL_RECOVERY_WINDOW_BUDGET=100
CAPITAL_BACKFILL_RETRY_SECONDS=900
CAPITAL_SUSPENSION_SYNC_ENABLED=true
CAPITAL_SUSPENSION_CACHE_FILE=./data/trading_suspensions.json
```

上限按 API 查詢區間，不是按 K 線根數。正常輪每檔最多 3 區間；慢速輪每檔最多 3 區間、整輪最多 100 區間，預設隔 15 分鐘續跑。停牌／純休市跳過不計 API 查詢額度。原有查詢節流、記憶體保護、去重 upsert 仍保留。

`refresh-stale` 回應的 `action=planning_at_group_start` 表示族群已排入，根數／工作數仍未統計，不是「有 0 筆待抓」。實際統計在 `/api/v1/backfill/control` 的 `group_plan`、`queued_jobs`，及資料狀態頁目前回補區塊顯示。族群規劃初版為 `control_version=3`，含週期目標修正的版本為 `4`。

### 週期目標修正（control_version=4）

```dotenv
CAPITAL_DAILY_BACKFILL_TARGETS=1m:1200,5m:1200,15m:1200,60m:1200,day:1200,week:560,month:100
```

上述是歷史補齊與達標判斷的目標，不是儲存上限。已經 1200 根的日線再取得 5 根新資料，仍保留全部 1205 根；週線超過 560、月線超過 100 也不截短、不拒寫。重疊日期僅 upsert 更新，不重複計數。

排程、網頁、API 和 CLI 共用各週期設定。網頁「自訂補齊目標」留空、API 不傳 `target_bars`、CLI 不傳 `--target-bars` 即自動選擇；明確指定數字則有意覆寫所選週期。例如 `--intervals week,month` 自動採 560／100，`--intervals week --target-bars 1200` 則刻意以 1200 為週線目標。

舊保存計畫沒有來源標記、且套用統一 1200 的預設者，於新程序取得工作鎖後依新設定重新規劃；自訂目標保留。已完成最新日期檢查、庫內根數已達降低後目標的歷史 pending 工作，會直接依實際根數完成，不再呼叫群益補到舊 1200。既有 K 線、檢查日期不動；尚未達標者保留區間續跑。

本次只改檔案，不動目前執行中程序或正式工作表。請自行安排安全暫停及重啟套用；新表與目標校正只會在之後執行新工作時生效。資料狀態頁各週期旁顯示設定目標，目前工作另顯示真正執行中的目標。

## 舊版重抓全部資料按鈕（control_version=6，已由版本 7 取代）

以下僅記錄舊流程；現行按鈕使用本文開頭的單一互斥協調端點，準備成功即開始，手動執行不再等待下一交易日。

`/data-status` 的「重抓全部資料」會先要求確認，使用現有商品主檔，準備全部 5 個市場、7 個週期。這是重查各週期設定的歷史範圍，不是從上市以來無限下載；不受上方市場／週期篩選或自訂根數影響。

依序送出 14 個 POST：`/api/v1/board-lot/backfill/prepare?interval=...&force=true` 與 `/api/v1/odd-lot/backfill/prepare?interval=...&force=true`；週期為 `1m,5m,15m,60m,day,week,month`。未傳目標根數，由後端讀取設定（一般 1200、週 560、月 100），並固定本次範圍與目標。兩端點不傳 `force` 時仍維持原本增量準備行為。

若已有工作執行或等待續跑，先按「安全暫停」，等工作停止再準備。準備過程持有工作鎖，不直接呼叫群益；既有 K 線保留，實際執行時重疊資料以時間鍵 upsert 更新。明確重抓會重設該範圍的舊工作游標，後續的續跑不再重設。已準備的各市場／週期合併保存至本機控制庫，跨日亦接續固定範圍，未完成前每日排程不覆蓋其斷點。記憶體暫停的恢復門檻照常保留。

14 組全部成功後仍維持暫停，需再按「繼續回補」，並符合登入連線、交易日、記憶體條件才開始抓取。中途失敗會停止後續準備並顯示已完成組數，不自動啟動；已準備的工作保留。若逾時，先查看狀態，勿立即重複送出。此版本只修改檔案，未替你重啟或觸發正式回補。

### 記憶體與狀態修正（control_version=5，2026-10-17）

不需要清空正式資料庫。新程序首次取得工作鎖後，會重新核對舊族群計畫與週／月目標；不刪 K 線、不把目標當儲存上限。此版本沒有重啟現有服務，也不會在測試時啟動群益。

商品清單按市場同步並釋放暫存；商品同步前後、族群規劃前後、查詢前後、提交並釋放資料後均量測程序記憶體。`/api/v1/backfill/control` 及狀態頁保留最多 32 筆階段樣本（時間、私有配置、實體使用、差值、是否 GC）。查詢已回來的資料會先完整提交，才因記憶體停止，確保續跑不重查該區間。

```dotenv
API_MEMORY_STOP_BACKFILL_MB=4096
API_MEMORY_RESUME_BACKFILL_MB=3072
API_MEMORY_RESUME_COOLDOWN_SECONDS=120
API_MEMORY_RESUME_STABLE_SECONDS=60
API_MEMORY_GC_INTERVAL_SECONDS=30
API_MEMORY_STAGE_DELAY_SECONDS=1
CAPITAL_BACKFILL_EMPTY_RETRY_SECONDS=86400
```

以上未設定即使用預設，不必修改 `.env`。停止後至少冷卻 120 秒，且多次觀察低於 3072 MB、持續至少 60 秒才自動續跑。手動按鈕與每日排程亦遵守；重新啟動的程序需重新觀察，不沿用舊程序的低水位計時。每次 GC 至少間隔 30 秒；正常狀態不因 `windows=0` 重複 GC。警告狀態的階段節流最多每 30 秒一次、預設 1 秒；不會對每檔額外睡一秒。這些是保護與診斷，不保證可回收 COM 原生記憶體；持續超限時保持等待，不能靠無限重試或單純提高門檻處理。

商品同步中斷時保留同一排程 ID，恢復後仍先完成兩組商品同步；已有 K 線計畫的記憶體暫停不會被下一次每日排程重新排隊覆蓋。

市場表拆分最新／長缺口／歷史／待分類等待；「已檢查至」可包含成功空回應或官方跳過，與最後成交 K 標記日不同。顯示無 K 線商品數與平均耗時樣本數，工作覆蓋率不是資料完整率。週／月舊暫存快照仍保留，但分析與初始化根數判斷只採期間已完成且寫入時間不早於該期最後交易日 14:00（台北）的資料；尚未重查的舊快照不視為完整。最後標記日保留原始觀察語意，不是完整期間保證。

## 隔離驗證

### 2026-10-18：記憶體恢復觀察與續跑條件分離

記憶體保護暫停的 API 工作，每 15 秒由背景恢復迴圈更新私有／實體記憶體、`memory_observed_at`、低水位觀察開始時間及 `memory_resume_ready`。即使休市、主行情斷線、手動暫停、正在退避或沒有可續跑的計畫，仍更新觀察結果；不因此登入、抓取、重排工作或解除手動暫停。API 不替 CLI 程序量測其恢復記憶體。

「記憶體已符合」只表示通過原有低水位穩定時間與冷卻條件；實際續跑仍要是可恢復的 API 工作、退避已到期、未手動暫停、沒有執行中 worker、群益行情已就緒、當天為交易日，而且存在已保存計畫／續跑範圍／中斷排程。工作、斷點與原暫停原因都保留。記憶體再次升高或無法量測，低水位計時重設並維持未就緒。

每次新的記憶體暫停會清除上一次的恢復就緒旗標與觀察時間。資料狀態頁顯示恢復觀察時間及「尚未符合／已符合」；已符合時仍提醒其他續跑條件，不把它當成工作已開始。本次沒有修改 `.env` 門檻、GC 節流或抓取連線生命週期。

離線驗證使用獨立暫存控制庫與模擬時鐘／記憶體／行情，不啟動實際 DLL、不連 MySQL。套用到既有程序仍需自行安排安全重啟；本次沒有重啟、恢復或更動正式控制庫。
