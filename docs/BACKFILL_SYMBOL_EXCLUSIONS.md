# 從自動抓取名單排除 TSLQ

2026-10-20 依使用者最新要求，將前文的 **TSLQ**（訊息中的 TLSQ 視為代號筆誤）整檔排除。設定檔 `config/backfill_excluded_symbols.json` 目前只有 `TSLQ`，不是排除整個指數分類。

## 適用範圍

七個週期 `1m / 5m / 15m / 60m / day / week / month`，一般及零股共用同一規則。初始化、逐檔增量、完整範圍重抓、日常最新根數回抓、由日 K 彙整的每日週／月工作，以及失敗重試都不會規劃 TSLQ。

既有計畫即使已包含 TSLQ，領取待抓工作時仍會排除；`force` 或 `only_symbols=['TSLQ']` 不能繞過。回復 running 工作、統計 pending 工作及舊版佇列操作亦套用規則，避免只擋新計畫卻從舊斷點再次抓取。

抓取儀表板的商品分母、已追蹤工作、失敗／待抓／執行中統計及資料日期改以剩餘合資格商品計算。這表示「不納入抓取範圍」，不是將 TSLQ 的失敗改成成功。

## 保留的資訊

- 不刪除既有 K 線、進度、失敗診斷、工作紀錄或商品主檔；沒有為套用規則而重寫 TSLQ 的工作狀態。
- 不修改 `instruments.is_active`，那是群益商品上市／有效狀態，不應拿來代替使用者抓取設定。商品主檔同步仍可正常更新 TSLQ，但不會解除此排除。
- 既有資料仍可供讀取及分析。明確指定單檔的歷史查詢／單次同步端點保留原功能，這份清單限制的是自動／批次抓取名單，不是資料存取權限。
- 之前兩個週／月異常期間的精準排除設定仍保留；在自動抓取時，整檔排除優先，已不必逐筆補齊 TSLQ 的其他異常日期。

## 生效及維護

設定在程序內快取，API／CLI 啟動時驗證。修改清單需安全重啟 API／CLI，已在執行的舊程式不會熱載入。正在查詢的區間應先提交並安全暫停，不強殺程序或直接更動被占用的工作。

程式修改與離線測試階段沒有重啟正式 API、沒有修改正式 MySQL。使用者後續已明確授權安全重啟與重新登入，正式套用結果見下方紀錄。

如日後確定要重新納入 TSLQ，從 JSON 清單移除它並安全重啟即可。保留的舊 failed 工作不會因此自動變成成功，應再明確決定是否重試。不要刪除 JSON 檔案或使用萬用字元；無效／重複／非大寫代號會報錯，不會靜默取消保護。
