# 獨立背景程序原生記憶體回收測試

日期：2026-10-19，Asia/Taipei。

## 結論與範圍

三輪實際 Windows 原生記憶體測試通過：每輪在新程序內使用 `VirtualAlloc` 配置並觸及 128 MiB，保留到程序正常結束；三個配置程序均以 exit code 0 結束，控制程序始終維持同一 PID，私有記憶體僅增加 0.019 MiB。

這驗證「把原生配置隔離到獨立程序後，結束該程序可回收其程序內記憶體」的機制。**本次沒有載入真實群益 DLL，尚未驗證群益登入、重新連線、訂閱恢復、K 線斷點續傳或長時間抓取。不能將它稱為完整 DLL 工作流程已通過。**

正式 API 尚未搬到新架構，原有約 4.16 GiB 私有記憶體沒有因此降低。

## 測試方法

新增 `scripts/measure_native_worker_recycling.py` 作為隔離測試原型，沒有修改正式服務程式或設定。

1. 透過既有唯讀端點確認正式 API 仍連線、回補已因記憶體暫停。
2. 控制程序每輪只建立一個測試子程序，實際配置 128 MiB 原生記憶體並逐頁觸及。
3. 使用 Windows 程序計數器量測配置前後、即將正常結束時的私有記憶體與工作集。
4. 控制程序另以 `OpenProcess` / `GetProcessMemoryInfo` 核對實際配置程序的計數器。
5. 透過 stdin 要求測試子程序正常結束；刻意不呼叫 `VirtualFree`，確保量測的是程序結束的回收效果。
6. 核對實際配置程序的 exit code 0，再建立下一輪程序。
7. 測試前後再比對正式 API 的 PID、連線及回補狀態。

Windows 虛擬環境的 `python.exe` 會另開實際解譯器。正式採計結果使用子程序自行回報的實際解譯器 PID，且要求外部量測與子程序量測相差不超過 4 MiB；啟動器 PID 單獨記錄，避免誤量只占約 0.8 MiB 的啟動器。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 17692 | 14.309 | 142.559 | 128.250 | 15.195 | 0 |
| 2 | 15592 | 14.348 | 142.598 | 128.250 | 15.195 | 0 |
| 3 | 9028 | 14.574 | 142.824 | 128.250 | 15.195 | 0 |

- 控制程序 PID：29764，三輪均未重啟。
- 控制程序開始：15.176 MiB；三輪後：15.195 MiB；增量：0.019 MiB。
- 三輪依序配置原生區塊合計 384 MiB，沒有同時建立三個程序或配置 4 GiB。
- 以「控制程序 + 實際配置程序」的私有記憶體計算，三輪程序結束前後的差額分別約 142.610、142.649、142.875 MiB，包含該子程序的解譯器用量。

- 本次不需強制結束任何程序；正常結束協定三輪均成功。

## 真實 DLL 測試尚未執行的原因

測試時以非阻塞方式確認既有 `data/capital_skcom.lock` 已被占用；沒有建立、覆寫或解除別人的鎖。正式 API 的群益連線仍就緒，依現有設計，不可同時讓另一個程序登入／操作群益 DLL。

下一階段需要暫時把群益連線的獨占使用權交給真實測試程序，並安排本機安全登入及測試後恢復。這會造成行情短暫中斷，雖然 API 與 MySQL 可以保持運作。本次未自行執行這項變更。

也尚未驗證退出程序前 K 線與游標提交、程序重建後自動登入及恢復訂閱；這些必須在測試版背景程序及相應整合測試完成後另外驗收。

## 重現指令

在 `capital_api` 目錄執行。腳本每輪會先檢查可用實體與提交記憶體，至少需有 512 MiB；只會正常結束自行建立的測試子程序。

```powershell
.\.venv\Scripts\python.exe -B -X utf8 .\scripts\measure_native_worker_recycling.py --payload-mib 128 --rounds 3 --api-base-url http://127.0.0.1:8000
```
