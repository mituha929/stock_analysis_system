## 提交後輪替與精確續抓

沿用正式 `CapitalWorkerService`、`BackfillRunner`、`MySQLCandleRepository`，不是手動關掉程序再重跑腳本：

1. 使用獨立的 `rotation_candles` 與一個1m工作，查2026/10/21～10/22，每次最多一個交易日。
2. 將測試 supervisor 的門檻降至真實配置用量的90%（224.4 MiB），以實測記憶體觸發，不竄改遙測、不注入假K線、不人工配置大量記憶體。正式API門檻仍3072 MiB。
3. 第一區間回傳後，`pending_windows=1`、`recycle_due=true`。在MySQL提交前嘗試輪替被拒絕，舊程序仍活著。
4. 正式repository將270根K線與游標在同一交易提交；另一個資料庫連線確認游標已持久化。只在提交後將**測試設定**恢復3072 MiB，再由正式runner的 `history_checkpoint(True)` 呼叫觸發已排定的輪替。如此替代程序不會因初始用量高於人工降低的測試門檻而立即被拒絕。
5. 舊程序PID21540正常退出（exit0），替代程序PID25340自動登入並收到3003。`recycle_count=1`、`forced_exits=0`、`pending_windows=0`，2330訂閱成功恢復。
6. 第二輪從資料庫持久化的10/22開始，不重查第一區間。再寫270根，合計540根且540個唯一時間；最後游標10/23、工作completed、owner_token清空。

背景程序私有記憶體約249.3 → 245.8 MiB；測試協調程序約30.2～30.6 MiB（不是正式API的用量）。這證明低門檻的提交後輪替與續抓路徑可運作，不等於4GB壓力測試，也不證明長時間原生記憶體增長根因已排除。
