# 資料狀態頁效能與續跑修正（2026-10-15）

## 實際原因

1. 原完整狀態 HTTP 查詢超過55秒仍未返回；健康檢查約0.23秒、控制狀態約0.02秒。瓶頸不在群益查詢或 HTML。
2. MySQL 估計 `candles` 約3682萬筆、`odd_lot_candle` 約2502萬筆。原版依五個市場各做七個日期查詢，工作排序亦重複執行。
3. 原日期 SQL 的 correlated MAX、改成 correlated ORDER BY LIMIT 的嘗試，都被實際執行計畫確認仍會讀取／排序每檔的多根 K 線，不是真正只取最後一筆。
4. 多個分頁／使用者的自動刷新同時累積慢查詢；原前端還會在 SQL 未回應前停用繼續按鈕，或在操作後等待整份狀態讀完。
5. 當時本機控制檔 payload 是空物件，沒有 plans。舊續跑端點因此直接返回「沒有待續跑工作」，即使資料庫仍有歷史等待工作。

## 修改

- 日期查詢改成 `GROUP BY symbol,interval_code, MAX(candle_time)`，執行計畫已確認為 covering index skip scan for grouping；沒有新增／變更正式索引。
- 三個整張市場合併一次、兩個零股市場合併一次查詢；工作排序只處理窄欄位一次，再讀取最新工作的錯誤內容。查詢數從原完整範圍約57次降至12次。
- HTTP 不再等待完整 SQL。首次顯示背景建立快照；之後先顯示上次快照，明確標示年齡與刷新狀態。一個背景讀取器、最多12組快照、同一範圍去重，避免多分頁放大讀取負載。
- 控制狀態獨立每5秒讀取；快照每15秒檢查，建置中亦沿用此間隔，不額外輪詢（2026-10-20 移除原本的2秒輪詢）。讀取狀態不鎖住操作，操作完成也不等待 SQL，操作結果不被刷新文字覆蓋。
- 續跑立即保存要求並回傳202；缺少本機計畫時，依選定市場／週期在背景重建。重複點擊只保留一個要求；等待群益、休市、建立計畫與失敗原因均可見。
- SQLite 狀態輪詢使用唯讀連線，不再每次 CREATE／INSERT。錯誤快取只保留文字，不保留可能引用查詢結果的 traceback。

## 量測與限制

使用現有大型資料庫做 SELECT-only 量測，不登入群益、不修改正式資料、不開新伺服器或重啟現有 API：

| 項目 | 本次量測 |
| --- | --- |
| 原執行中 API 完整查詢 | 超過55秒逾時 |
| 新版獨立 ASGI 首次回應 | 約0.047秒，明確回報背景建立中，尚無 items |
| 背景建立35個市場／週期與10筆日誌快照 | 約16.39秒 |
| 已完成快照的獨立 ASGI 回應 | 少於0.01秒 |
| 改寫後兩個實際 K 線日期 SQL | 此次約0.062秒、0.125秒 |

首次全量快照仍需等待背景讀取完成；不是16秒資料在0.047秒全部讀完。背景時間含既有舊版重複查詢負載，會隨資料量、快取及同時工作改變。ASGI量測不含真實瀏覽器網路／渲染，不能直接當作部署後所有請求的延遲保證。
