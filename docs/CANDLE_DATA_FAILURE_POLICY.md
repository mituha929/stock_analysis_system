## 每次驗證，不等到第五次才驗證

`parse_kline_record` 以 Decimal 精確解析整數，拒絕負值、小數、NaN／Infinity、格式錯誤及大於 `18446744073709551615` 的成交量；不再使用 `int(float(...))`。合法整數形式的小數／科學記號仍可解析，但不截斷非整數。已解析的 Candle 在 runner、SQL 寫入入口及直接同步入口再次驗證。

來源不合法會拋出獨立 `CandleDataError`，保留時間、原始成交量文字、可取得的原始 K 線文字及批次行號。COM callback、原生服務包裝、worker IPC 都保留其資料錯誤分類，不冒充連線中斷或資料庫故障；一次 callback 發現錯誤後，不會僅丟棄壞列再把剩餘列當作完整區間成功寫入。互動歷史 GET／同步則回應422，不自行建立批次工作或累計批次重試。

不取絕對值、不歸零、不加2^32、不放寬資料庫型態，也不刪除既有合法 K 線。對來源資料缺陷不做未經證實的「溢位修復」。

## 連續失敗規則

| 時點 | 工作及進度 |
|---|---|
| 第1～4次同區間資料錯誤 | 工作 pending、釋放擁有者、整批不寫入、保留原斷點；回補暫停至少15秒後重試 |
| 第5次同區間資料錯誤 | 原工作 failed、保留資料及斷點；本輪繼續其他商品，不自動領取此 failed 工作 |
| 同一區間成功提交 | 資料、下一日期及計次歸零一起提交；不包含單純拿到資料或尚未提交的成功 |
| 查詢區間或游標改變 | 新區間從1次計起，不帶入另一區間的失敗次數 |
| 資料庫或 SDK／IPC 連線故障 | 沿用整輪安全暫停，不增加股票資料錯誤次數，不一次把大量股票判 failed |

工作鍵是 `job_table + job_id`，區間識別為原游標及查詢起訖日。新的 `candle_backfill_data_failures` 附加表保存當前區間、連續次數、原始診斷與首末失敗時間，不 ALTER 大型 K 線／工作表；進度表的 `next_date`、本輪已收數、空區間數不因資料失敗前進。既有 `attempt_count` 仍是總領取數，不能用它推定連續失敗。

資料錯誤計次、pending／failed 及工作擁有者釋放在同一 MySQL 交易。連續計次跨 API／CLI 或 DLL worker 重開保留。若連計次資料庫都無法使用，安全暫停為 database，不捏造計次或繼續盲目寫入。

自動恢復檢查尊重15秒時間，手動暫停仍須使用者解除。使用者明確按繼續可提前重試，但不清空計數；「重試失敗」亦不因重新排入就抹除舊計數，來源修正後成功提交才歸零。已確認 failed 不會由一般自動恢復重新領取；明確完整重抓／重新規劃仍可能重新包含該商品，不能把這當永久股票黑名單。

來源日 K 的分段保存不等於週／月彙整區間完成，彙整工作要到其結果及游標提交才清零；半途失敗繼續沿用整個彙整視窗的計數，避免每次來源前半段成功就無限原諒後半段錯誤。
