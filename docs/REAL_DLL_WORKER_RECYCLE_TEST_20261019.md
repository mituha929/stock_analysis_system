## 結論

最終短程整合測試通過。兩個不同 Windows 程序依序使用 `.env` 自動登入真實群益 DLL，確認報價就緒、訂閱請求成功，並以正式使用的 `BackfillRunner`、V2 batch 計畫與 MySQL repository 完成跨程序斷點續抓。

第一個程序在一個真實 K 線區間提交後，透過測試鉤子要求安全暫停並正常退出；第二個新程序讀取相同的持久計畫與 MySQL 斷點，只查下一天。沒有使用模擬 K 線或 VirtualAlloc 代替實際 DLL。

**這證明短程整合流程可行，不代表正式 API 已啟用背景程序輪替，也不是 4 GiB 壓力測試或記憶體洩漏根因修復。**

## 記憶體與回收

下列單位為 MiB，量測對象是實際載入 DLL 的解譯器，不是 Windows venv 的小型啟動器。

| 時點 | 程序 26844 | 程序 9920 |
| --- | ---: | ---: |
| 登入前私有記憶體 | 25.578 | 25.863 |
| 報價連線／訂閱後 | 240.297 | 240.582 |
| 收到歷史 K 線後 | 461.578 | 461.273 |
| 關閉服務後、程序退出前 | 459.637 | 459.324 |

正常退出前仍保有約 459 MiB；父程序用 OS handle 核對兩個實際解譯器皆為退出碼 0，並確認 DLL 鎖釋放。第二個程序從約 25.9 MiB 的新程序基準開始，而不是承接第一個程序約 459 MiB 的配置。這支持以程序邊界回收程序內配置；不是宣稱每次 `disconnect` 本身就能回收同等用量，也沒有把整機可用 RAM 的變動當成精確回收量。

正式 API PID 一直維持 27700；測試背景程序退出時，API 私有記憶體約 1925.6～1925.7 MiB。**原 API 仍載有既有 DLL 與配置，並未因此回到低記憶體基準。**

最後恢復正式抓取後的兩次唯讀檢查，API 私有記憶體約 2069.8／2069.7 MiB，`quote_ready=true`、`state=running`、`worker_active=true`、`pause_requested=false`；商品由 3548 變成 3555，處理數由 33,288 增加到 33,291，區間數由 47 增加到 53。既有 2048 MiB 警示與 4096 MiB 暫停保護仍保留，未提高上限。

## 正式資料與恢復

- 正式抓取先經 API 安全暫停，確認 worker 已停，才持有其跨程序 worker lease，避免恢復執行緒或排程在交接時搶跑。
- 正式 API 主動斷線且 DLL 鎖可取得後，才開始第一個測試程序；兩個測試程序不會同時登入。
- 真實 K 線與測試工作只寫入新建隔離資料庫 `capital_dll_test_31b3ed908462`。
- 測試期間，所選正式工作斷點逐列比對相同，正式保存計畫亦逐項比對相同；沒有刪除或重建正式 K 線與工作。
- 測試後先確認測試程序全部退出、鎖已釋放，再恢復原 API 的群益連線及保存計畫。沒有重啟、強制終止或替換正式 API。
- MySQL 與 HTTP API 持續運作；群益連線在交接期間短暫中斷。
- 帳密只在程序記憶體及本機登入請求中使用；命令列、報告與事件輸出不包含帳密。
