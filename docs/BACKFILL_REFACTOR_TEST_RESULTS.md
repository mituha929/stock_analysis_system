# K 線回補改寫與測試紀錄

日期：2026-10-15

後續「狀態頁過慢／續跑無反應」修正及更新至244項測試的紀錄，另見 [狀態頁效能與續跑修正](DATA_STATUS_PERFORMANCE.md)。下列232項為第一階段改寫的測試結果。

## 本次完成範圍

1. 所有週期初始化目標統一為1200根；歷史不足完成有界探查後標示不足，不每天重跑初始化。
2. 保留全部既有歷史，逐檔依實際 K 線與完整同步斷點建立增量範圍，不以工作寫入時間推定資料齊全。
3. 每日交易日18:30更新 `1m,5m,15m,60m,day`，自動範圍只使用已收盤日期。
4. 當週／月最後交易日當日加入週／月線，並按完整期間切段，不寫入拆開的期間彙總。
5. 沿用交易日曆、官方年度休市表快取及備援設定；休市日不啟動，錯過的週／月在下一交易日補跑，成功標記按市場保存。
6. 每段 K 線與下一查詢游標在同一 MySQL 交易提交；崩潰或寫入失敗不會把未寫入範圍誤當完成。
7. 連線錯誤先有界重連；恢復不了或 MySQL 故障就安全暫停，後續工作保留等待。個別商品錯誤才標失敗。
8. 網頁、API與CLI共用持久暫停／續跑控制；可在不停止 FastAPI 的情況下暫停回補。
9. 背景批次不再長時間持有 HTTP 操作鎖；獨占工作鎖避免兩個新版本 worker 同時領取工作。舊過長等待工作保留為 `superseded`。
10. API／CLI共用查詢間隔，預設0.8秒，按 API 查詢次數而非 K 線根數等待，並重用原生連線。
11. 資料狀態頁增加模式、目前商品／區間、已提交斷點、暫停原因與記憶體；日誌區分手動、連線、資料庫及記憶體暫停。「工作覆蓋率」不等於資料完整率。

每日排程原有的整張、零股兩組商品主檔同步先決條件保留：兩組成功才開始 K 線。

## 記憶體

- 每次請求清空接收暫存，寫入後清除區間結果引用；批次結果不放入互動快取。
- 互動歷史快取最多20組，每組1200根；維護迴圈主動清除到期項目。
- API與CLI監控各自程序記憶體；預設2GiB警示、4GiB安全暫停，定期／壓力下回收 Python 物件。
- 狀態頁避免重疊累積未結束的 MySQL 狀態查詢；本機進度獨立讀取。

## 重現方式

在 `capital_api` 目錄執行：

```powershell
.\.venv\Scripts\python.exe -B -X utf8 .\scripts\test_backfill_recovery_offline.py --all
.\.venv\Scripts\python.exe -B -X utf8 .\scripts\test_backfill_memory_offline.py
.\.venv\Scripts\python.exe -B -X utf8 .\scripts\test_backfill_mysql_isolated.py
node --check .\app\static\data-status.js
```

MySQL測試需要建立／刪除獨立測試資料庫的權限；沒有權限就失敗，不會改用正式資料庫。

## 生效與尚未驗證的部分

- 目前執行中的 API 仍是舊版本。本次不重啟；先安全停止舊版回補，再由使用者安排重啟套用。新增進度表會在新版本建立回補計畫時自動建立。
- 本次未對新版本做真實群益長時間壓測或全市場耗時測試；也未對新版頁面做人工視覺驗收。離線 Python 記憶體測試不能證明原生 DLL 永不增加記憶體，且不包含 MySQL、Ollama 等其他程序。
- 0.5秒仍只是可設定的候選值，沒有改成預設或以真實群益驗證。
- 1200根月線約需100年，通常不可能取得。連續3個空查詢區間停止探查是有界策略，不能據此證明更早資料不存在。
- 官方目前使用的歷史 K 線函式以整股成交計算。保留零股工作流與表名，不代表取得真正零股成交 K 線；沒有擅自更換來源或補造資料。
