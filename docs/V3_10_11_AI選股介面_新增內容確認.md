# V3.10～V3.11：AI 選股介面新增內容確認

- 文件日期：2026-10-30（Asia/Taipei）
- 狀態：**使用者已確認，2026-10-30依本文件實作；正式環境整體驗收待完成**。
- 本文件保留設計確認基準；實際功能、API及測試結果見 [AI選股操作說明](V3_AI_PREVIEW.md)。最初文件交付僅新增Markdown，後續實作由使用者另行授權。
- 階段編號：依《V3 提醒／選股系統開發流程》的「最終開發順序」，不是前面的主題章節編號。

## 1. 本次要完成什麼

讓自己與不熟悉技術指標的家人，可以在網頁輸入選股需求，先看懂系統如何解讀，確認後才執行。

本次流程：

**輸入需求 → 解析／釐清 → 白話條件預覽 → 使用者確認 → 程式選股 → 顯示結果與資料狀態**

兩階段分工：

| 階段 | 新增內容 |
|---|---|
| V3.10 | AI 選股網頁、模糊需求引導、白話規則與 AND／OR 分組、AI 假設及未解決條件預覽 |
| V3.11 | 確認與版本綁定、後端再次驗證、呼叫既有選股引擎、結果與資料品質／部分完成標示 |

不是只做 API；會在目前 `/v3` 功能驗證台新增「AI 選股」頁籤。

## 2. 現有功能與本次新增的界線

目前已存在：

- V3.8：`POST /api/v1/ai/rules/parse`，自然語言轉規則草稿。
- V3.9：`POST /api/v1/ai/rules/validate`，驗證欄位、型態、範圍與規則結構。
- `GET /api/v1/rules/fields`：欄位白名單。
- `POST /api/v1/screener/run`：讀取 MySQL，執行規則與排序。
- `/v3`：已有規則測試、提醒、通知、選股及儲存策略等人工操作介面，但沒有 AI 解析整合頁面。

目前選股回應已有資料日期與 `complete`／`ranking_complete`，但現有選股服務仍明示「未驗證收盤或資料新鮮度」。因此本次不能只替舊結果換版面，**需要在後端新增 AI 選股使用的完整期間與資料新鮮度檢查**。

## 3. 第一版不是完整多輪聊天

第一版採「引導式 AI 選股」：

- 有自然語言輸入框、釐清選項、條件預覽及執行結果。
- 釐清時顯示已補充的條件，再產生一份新的完整輸入供解析；不能把補充內容藏在不可見的聊天記憶裡。
- 使用者可以修改需求後重新解析。
- 不把「再加上 RSI 小於70」「把剛才條件放寬」當成可直接修改舊規則的對話指令。
- 完整上下文、多輪策略新增／刪除／修改留到 V3.12。

可以做得像對話般容易操作，但不宣稱已具備完整聊天機器人的能力。

## 4. 介面與操作順序

### A. 輸入需求與選股範圍

提供：

- 需求輸入框。
- 股票範圍：市場、自選股或指定股票，重用既有選股能力。
- 市場與 K 線週期選項。
- 「解析條件」按鈕。
- 簡單範例與「我不清楚，先解釋差別」引導。

建議預設為「上市＋上櫃、日 K、整張歷史資料」。市場、資料來源與週期由使用者明確選擇，不交給目前尚未支援這些項目的 AI 解析器自行猜測。

若輸入文字與所選範圍不一致，例如文字要求「上櫃」但選項為「上市」，必須提示確認；不可忽略原句或直接覆寫選項。

### B. 顯示解析與白話預覽

保留並展示：

1. 原始需求及補充內容。
2. 最終市場、股票範圍、資料來源與 K 線週期。
3. 每條規則的白話說明。
4. 「全部符合（AND）」及「任一符合（OR）」的巢狀分組。
5. AI 假設：原詞、如何量化、可修改的門檻。
6. 尚未解決的條件與不能執行的原因。

白話規則應由程式依驗證後的規則樹產生，不再讓模型自由改寫，避免解說與實際條件不同。

例如 `ma20` 應解釋成「所選週期最近20根 K 線的平均收盤價」；使用週 K 時不可仍說成20個交易日。金額、成交量與量比的單位，也必須與實際資料定義一致；單位尚未確認的欄位，不提供容易誤導的量化選項。

JSON 放在可展開的進階區，不要求一般使用者閱讀或編輯 JSON。

### C. 確認並執行

- 沒有可執行規則、仍有未解決條件或驗證失敗時，禁止開始選股。
- 使用者確認最終範圍、規則與全部 AI 假設後，才能按「確認條件並開始選股」。
- 執行中禁止重複送出；不得顯示沒有真實資料依據的百分比進度。
- 顯示「執行中／完成／部分完成／失敗」，錯誤要說明可採取的下一步。

## 5. 模糊需求如何處理

| 類型 | 輸入例子 | 行為 |
|---|---|---|
| 明確條件 | RSI 小於70 | 產生規則草稿，仍須使用者確認 |
| 可量化但模糊 | 趨勢比較強、風險不要太高 | 顯示建議解讀與假設，確認前不執行 |
| 無法事前保證 | 找會賺錢、一定上漲、穩賺的股票 | 先釐清，不產生可執行規則 |
| 不支援的資料 | 找公司獲利成長、看新聞選股 | 明確說明目前資料不支援，不用技術分數代替 |
| 個人持股問題 | 本金虧10%就賣出一半 | 說明需要持股、成本及本金等另一套功能，不套用為技術風險分數 |

對「找會賺錢的股票」，建議顯示：

> 我可以幫你篩選值得觀察的股票，但無法事先確定哪檔會獲利。你比較想了解近期表現較強、上漲後回檔，還是公司本身的財報獲利？

上述是研究方向，不是獲利承諾，也不是未經確認就啟用的策略。

不支援或尚未釐清時，沿用 `status=needs_clarification`、`rule=null` 的保守契約。若一句話同時包含合法與無法處理的要求，不得只拿合法部分執行。

Prompt 與後端都需保護；但不能宣稱僅靠關鍵字或 JSON 驗證就能理解所有語句。最終仍保留人工確認。

## 6. 資料日期與品質

### 原則

- 只分析已儲存在 MySQL 的資料；不因使用 AI 選股而登入群益、觸發回補或重新抓行情。
- 先驗證可使用的完整期間，再做價格／成交量預篩與規則判斷，避免用舊資料預篩後造成錯誤排除。
- 日 K、週 K、月 K 分別對照最近已完成交易日、週與月；使用現有交易日曆，考慮休市、週末與收盤界線。
- 分鐘 K 必須另外處理盤中已結束時間桶與盤後最後有效區間；不直接套用「距今天幾天」判斷。
- 個股停牌或無成交不等於系統沒有查過，須區分資料缺口與個股狀態；沒有可信來源時標示無法確認，不推定其一定正常或已停牌。
- 不補造 K 線，不因排除而刪除既有資料。

### 結果分開呈現

- 符合條件。
- 不符合條件。
- 資料缺失／不足。
- 資料過期或完整期間尚未確認。
- 分析錯誤。
- 尚未處理。

第一版建議將過期或完整期間未確認的資料排除於正常符合名單，但保留原因供查閱。

每檔顯示最新可用 K 線日期與週期；資料寫入時間另列為輔助資訊。**寫入時間很新，不代表內容日期很新。**

## 7. 修改後重新確認與後端保護

- 修改原文、補充內容、市場、股票清單、週期、資料來源、門檻或排序等執行設定，都會使原確認失效。
- 每份預覽有版本識別；執行請求必須對應使用者最後確認的那一份。
- 執行前，後端再次驗證整份選股設定及規則，不只信任前端核取方塊。
- 若採用預覽憑證，憑證須綁定規則及完整執行設定；不能拿舊憑證換新條件。預覽過期或服務重新啟動時，要求重新預覽與確認。
- 舊解析請求若比新請求晚回來，不能覆蓋新輸入或讓舊規則重新變成可執行。
- 同一畫面的連點不能重複送出；後端沿用既有選股互斥鎖，同時掃描時明確回報忙碌。
- 原文視為資料，不得成為任意 SQL、程式碼、系統指令或額外操作授權。

第一版不新增聊天歷史資料庫或多使用者權限系統；現有共用資料的限制不能被誤稱為已做到家庭成員隔離。

## 8. 結果、排名與部分完成

顯示股票代號／名稱、符合原因、價格、技術方向／風險分數、資料日期、警告及排序方式。提醒使用者分數不是勝率、報酬率或保證不虧損。

清楚區分：

- 掃描完成：選定範圍的商品皆已處理，不代表每檔都有可用資料。
- 部分完成：仍有商品未處理；排名僅代表已處理且可評估的部分。
- 顯示筆數限制：即使掃描完成，也可能只顯示前20檔，與掃描未完成不同。

假設有2,000檔、只處理600檔，應顯示：

> 本次掃描部分完成：已處理600／2,000檔，其中12檔符合條件，其餘1,400檔尚未評估。以下排名不是全市場排名。

沒有符合結果時，不自動放寬條件。可以建議使用者修改，但需重新預覽及確認。

以上數字及後續介面範例均為示意，不是真實選股結果。

## 9. API 與程式整合方向（名稱待實作時定稿）

1. 重用現有解析、欄位探索及驗證服務。
2. 增加預覽與確認執行的後端契約，綁定最終規則、範圍與版本；不能只是前端依序呼叫 parse 後立刻呼叫 screener。
3. 重用既有選股引擎及排序，不另外建立另一套指標計算。
4. 補上 AI 選股路徑的資料完整期間／新鮮度政策與狀態回應。
5. AI 僅在需求解析時呼叫本機 Ollama，不逐檔呼叫模型。
6. 保留原本手寫規則、提醒、通知及儲存策略 API 的相容性；若需擴充共用回應或服務，要有回歸測試，不默默改變既有策略結果。

預計涉及現有 `app/static/v3.html`、`v3.js`、相關樣式、`app/api/ai_rules.py`、`app/ai/` 與 `app/services/screener_service.py` 等；新增檔名及是否需要新的暫存預覽儲存元件，實作前再確認。

- V3.12：自然語言增刪改既有策略、完整多輪聊天及長期上下文。
- V3.13／3.14：AI 確認後直接建立提醒或儲存策略；既有人工功能不刪除。
- V3.15：定期執行選股與新增符合股票通知。
- 自動買賣、下單、預測一定獲利、個人持股減碼比例。

- 為此功能修改 K 線回補政策或刪除歷史資料。

## 11. 驗收案例

| 編號 | 情境 | 預期結果 |
|---|---|---|
| A01 | 股價高於 MA20，RSI 不超過70 | 白話與執行規則一致；不把「不超過」反轉為大於 |
| A02 | AND 中包含 OR 群組 | 清楚顯示全部／任一與分組，不攤平成全部符合 |
| A03 | 比較強、風險不要太高 | 顯示假設及門檻，確認前不可執行 |
| A04 | 會賺錢、下個月一定漲 | 進入引導釐清，不回傳可執行的保證獲利規則 |
| A05 | 合法條件＋不支援的新聞／財報要求 | 不忽略後半句，不拿部分規則執行 |
| A06 | 文字與市場／週期選項衝突 | 提示確認，不靜默覆寫或混用週期 |
| A07 | 修改1.5倍為2倍，或修改股票範圍 | 原確認失效，顯示最新版本，需重新確認 |
| A08 | 舊解析晚於新解析回傳 | 舊結果不能覆蓋新版本 |
| A09 | JSON 合法但 RSI 門檻120、未知欄位或條件矛盾 | 範圍／欄位錯誤必須拒絕；明確同欄位衝突提示修改，不宣稱能解決所有語意矛盾 |
| A10 | 資料過期、只有未結束週月 K 或缺少指標歷史 | 不列為正常符合結果，顯示原因與日期 |
| A11 | 遇到週末、休市或可信停牌狀態 | 正確區分市場休市、個股狀態與資料缺口 |
| A12 | 掃描超時／只顯示前20檔 | 分別標示部分完成與顯示筆數限制 |
| A13 | 沒有符合股票 | 不自動放寬條件，不宣稱其他未處理股票也不符合 |
| A14 | 模型離線、回應逾時、JSON 無效 | 顯示原因，不用空規則掃描全市場，也不無限重試 |
| A15 | 連點執行、另一個掃描正在進行、使用舊預覽版本 | 不重複啟動；忙碌或版本失效時明確拒絕 |

驗證順序：

1. 使用模擬模型、固定日期與行情資料，測規則、狀態及資料政策。
2. 使用隔離資料庫及前端測試驗證預覽、確認、版本失效、結果分類及重複點擊。
3. 使用本機 Ollama 驗證少量明確／模糊輸入；不需登入群益。
4. 使用少量指定股票，唯讀驗證實際 MySQL；再依結果安排較大範圍驗收。

不為測試自動重啟正式服務，不登入群益、不啟動回補、不向正式提醒／策略資料庫新增測試紀錄。
