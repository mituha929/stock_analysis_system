# 成交量越界錯誤診斷

日期：2026-10-19，Asia/Taipei。

## 已確認的直接原因

目前回補在 TSLQ、`month`、2018-02-01～2022-05-31 的區間發生 MySQL 1264：`Out of range value for column 'volume' at row 1`。

在群益已連線、回補 worker 未執行且 API 私有記憶體低於 1536 MiB 的條件下，只呼叫一次既有唯讀歷史 API：

```text
GET /api/v1/history/candles/TSLQ?interval=month&start_date=2018-02-01&end_date=2022-05-31
```

回應共 52 根 K 線，其中 20 根的成交量為負值。部分樣本：

| K 線日期 | 回應中的 volume |
| --- | ---: |
| 2018-02-01 | -1273379155 |
| 2018-03-01 | -229558559 |
| 2018-04-02 | -2128051720 |
| 2018-06-01 | -2065964440 |
| 2018-09-03 | -1282264045 |

整個回應的最小成交量為 -2128051720，最大為 2107009838。

正式 `candles.volume` 已在先前唯讀 schema 查核中確認為 `BIGINT UNSIGNED NOT NULL`，只接受 0～18446744073709551615。負值無法寫入，足以直接解釋這次 1264。`row 1` 指本批 INSERT 的第一筆值，不是資料庫內既有的第 1 列。

本次沒有將這些回應寫入 MySQL、沒有修改欄位型態或成交量。GET 會使用既有歷史連線，並更新有容量限制的互動快取。

## 程式處理缺口

1. `parse_kline_record()` 使用 `int(float(volume_text))`，沒有拒絕負成交量。
2. `Candle.volume` 目前只有 `int` 型態，沒有非負與 MySQL 上限的驗證。
3. `transaction()` 將資料值錯誤也包裝為 `MySQLRepositoryError`，runner 因而以資料庫問題暫停整輪。既有自動恢復邏輯可能再次嘗試相同問題區間。

另以純離線解析確認一個獨立的精度缺陷：合法的 unsigned BIGINT 上限字串 `18446744073709551615` 經 `int(float(...))` 變為 `18446744073709551616`，亦會越界。這不是本次負值的直接原因，但應一併修正為精確的整數解析。

## 還不能確定的部分

本次取得的是 API 解析後的歷史回應，沒有捕捉 DLL callback 原文或量到 DLL 內部計算過程。負值落在 signed 32-bit 範圍內，值得調查來源是否發生成交量溢位，但不能僅憑這個特徵就把負值加上 2^32、取絕對值或歸零。

## 建議修正方向（2026-10-19 診斷當時尚未實作）

- 精確解析成交量整數，並驗證非負及儲存上限。
- 保留錯誤股票、時間、來源成交量原值與查詢範圍供追查。
- 將不可重試的資料錯誤與資料庫連線中斷分開，保留失敗區間的原斷點、隔離該工作，讓其他商品可繼續。
- 不以放寬欄位為 signed、停用嚴格模式或任意改寫成交量掩蓋資料異常。

參考：[MySQL 整數範圍](https://dev.mysql.com/doc/refman/8.4/en/integer-types.html)、[越界值處理](https://dev.mysql.com/doc/refman/8.4/en/out-of-range-and-overflow.html)。
